# 山十 行先予定表 Ver.4.0

## Ver.4 の目的

Ver.3系で個別に修正していた「予定変更」「開始」「終了」「端末同期」を、1つの予定エンジンとして整理した基準版です。

## 予定処理

- 予定は `public.schedules` に共有保存
- Supabase Cronが毎分 `public.process_due_schedules()` を実行
- PC・スマホ・タブレットを閉じていても開始・終了を処理
- 開いている端末も同じDB関数を補助実行し、Cron遅延時に自動復旧
- `employee_status` と `schedules` はRealtimeで全端末へ通知
- Realtimeを取りこぼしても通常15秒、大型表示5秒の再取得で復旧

## Ver.4で修正したポイント

### 1. 予定変更

未開始の予定を編集すると `start_done` / `end_done` / `before_snapshot` を必ず初期化します。古い実行結果が残ったまま新しい日時を判定しないようにしています。

### 2. 開始

開始時刻を迎えた予定を時刻順に処理し、その時点の社員状態を `before_snapshot` に保存してから予定状態へ切り替えます。

### 3. 終了

終了時は「古い別予定が存在するか」ではなく、**現在本当に実行中の予定のうち最も新しく開始した予定**を再判定します。

- 別の実行中予定がある → その予定を再適用
- 別の実行中予定がない + 直帰 → 外出/直帰
- 別の実行中予定がない + 予定前へ戻す → `before_snapshot` を復元
- それ以外 → 在席/本社へ戻す

このため、長時間の古いテスト予定や重複予定があっても、終了処理が不自然に止まりにくくなっています。

### 4. 二重実行対策

DB側で `FOR UPDATE SKIP LOCKED` と実行フラグを使用しています。Cronと端末補助処理が同時に動いても同じ予定を重複処理しにくい構成です。

## 最初に実行するSQL

Supabase SQL Editorで `SETUP_V4.sql` を新しいQueryとして1回実行してください。

既存の `schedules` データは削除しません。テーブル・RLS・Realtime設定も維持したまま、予定処理関数と編集保護トリガーをVer.4へ更新します。
